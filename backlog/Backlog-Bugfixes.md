## Classification

**Here:** Prod deviation, regression (`xfail`), known misbehavior, review with clear fix/remove outcome; plus `## Document Review Findings` (docs corrections).
**Not here:** New behavior, UX, models, research — see feature backlog in `Backlog.md`.
**Versioning:** completed bugfixes → **PATCH** only in `version.py` (no minor bump). Docs-only findings: no version bump unless asked.
**Document Review Findings:** After the agent corrects the docs → move straight to `Backlog-Erledigt.md` (skip Verifications Pending). See skill `doc-review-findings`.

### `## Bugfix Verifications Pending`

Fix is **implemented** (code + tests + optional PATCH in `version.py`), but **prod/live acceptance** is still pending.

- Move item from the thematic bugfix chapter here once the fix is committed — **not** directly to `Backlog-Erledigt.md`.
- Briefly note what changed (commit/version) if helpful.
- After successful verification: remove from this chapter → `Backlog-Erledigt.md` (`### Bugfix …`) with `- [x]`.
- If verification fails: return to open bugfix chapter or formulate follow-up; document PATCH if applicable, but do not archive as done.

## New Bugs (Do not remove this chapter — even if empty)

- [ ] **Every tariff must carry a `land`; the tariff catalog and its validation allow tariffs without one:** the shipped `share/config/tariffs.json` is fine (0 of 50 without `land`), but `share/config/tariffs.example.json` (4 of 6) and the test fixture `tests/fixtures/backtesting/tariffs.json` (4 of 7: `fixed_25ct`, `fixed_37ct`, `fixed_35ct`, `monthly_test`) have tariffs without `land`, and `house_config/tariffs_store.py` (`_import_tariff_spec` / `_export_tariff_spec`) plus `share/config/tariffs.schema.json` only require it for `spot_hourly` / `ex_post_spot` / `monthly_market`. Effect: with a Land filter set, such tariffs silently drop out of the tariff selects in the Szenarienkonfigurator (only the already saved one stays visible), so the filter hides valid choices without any hint. Found by the UI persistence tests (scenario editor). Fix: make `land` mandatory for all tariff types in the schema and the loader (fail loud, no implicit fallback), give every tariff in the example file and the fixture a `land` (then adjust the tests that rely on the land-less fixture tariffs, e.g. `tests/apptest/test_persist_scenarios_apptest.py`, `tests/test_planning_editors.py`, and check `tariffs.minimal.json`), and add a validation test that rejects a land-less tariff. The user-defined pseudo tariff `__user_fixed__` ("Eigener Festpreis") is not a catalog entry and stays exempt.
- [ ] **Profile geo/PV defaults swallow a legitimate `0`:** `house_config/profiles_store.py::_profile_geo_and_csv_fields` uses `float(raw.get(key, default) or default)`, so `default_pv_tilt = 0` (flat roof) is saved and loaded as `25`, `latitude = 0` as `48`, `longitude = 0` as `10` — silently, no error. Found by the UI persistence tests (level 1, house profile); regression test is `xfail(strict)` in `tests/apptest/test_persist_house_profile_apptest.py` (`_KNOWN_BUGS`). Fix: distinguish missing/`None`/`""` from `0` (fail loud for invalid values, `.cursor/rules/no-implicit-fallbacks.mdc`); remove the `xfail` entry with the fix. Repro: set `Neigung` to 0 in Hauskonfigurator → new session shows 25.

- [ ] **Battery form accepts `max. SoC` below `min. SoC` without any message:** `ui/planning_battery_form.py` saves e.g. `battery_max_soc = 5` with `battery_min_soc = 10` (no validation in the form or in `house_config/battery_normalize.py`), leaving an unusable SoC window. Found by the UI persistence tests (T3); regression test is `xfail(strict)` `test_t3_battery_max_soc_below_min_soc_is_rejected`. Fix: validate `min_soc < max_soc` (store and form, fail loud); confirm the intended rule (strict or equal allowed) first.
- [ ] **House profile: `persons = 0` of a Haus Wärme consumer is silently turned into 2:** the widget allows `min_value=0`, but `house_config/profiles_thermal_annual.py` uses `int(_raw_thermal_field(raw, "persons") or 2)`, so 0 is saved as 2 and the next session shows 2 (same `or default` pattern as the profile geo/PV defaults entry above; other `or <default>` spots in `profiles_consumers.py` / `profiles_thermal_annual.py` should be reviewed together). Found by the UI persistence tests (T2); regression test is `xfail(strict)` `test_t2_boundary_values_roundtrip[wp-persons_0-0]` in `tests/apptest/test_persist_consumers_apptest.py` (`_KNOWN_BUGS`). Fix: distinguish missing/`None` from 0, or raise the widget minimum to 1 if 0 persons is not meaningful (decide first).
- [ ] **House config: choosing "— neu —" silently creates a profile and jumps back to the previous one:** selecting `— neu —` in the profile select (`ui/house_config_profile_form.py::_render_profile_selector`) renders the new-profile form with the default label "Mein Haushalt"; as the form is `ready`, autosave (`_perform_house_profile_save`, `is_new=True`) writes the profile `mein_haushalt` to `house_profiles.json` immediately (empty consumers, defaults 4500 kWh/a, 48.2/11.0) and puts the profile **id** into `house_profile_select_pending`. `_align_profile_select_session` only knows display labels (`id_by_display`), so the id is rejected and the select falls back to the previously selected profile. Result: the user never gets to edit the new profile, and a "Mein Haushalt" profile appears in the list unasked. Found by the UI persistence tests (level 1, L8); regression test is `xfail(strict)` `test_l8_new_profile_selection_does_not_jump_back_to_previous_profile` in `tests/apptest/test_session_switch_apptest.py`. Fix (decide first): either do not persist a new profile before the user changed anything (and keep the select on "— neu —"), or set the pending select to the display label of the created profile. Check the same pending-id pattern in the scenario editor (`scenario_editor_sections.py:374`) and the component forms.
- [ ] **House config (browser only): the first edit after opening loses the input and creates a "Mein Haushalt" profile:** in a real browser (Playwright against `streamlit run app.py`), in roughly 60 % of page opens the profile select (`house_profile_select`) reads `— neu —` on the first rerun caused by the user (instrumented `_sync_profile_session`: `scope=__new__`, `sel=— neu —`). The new-profile form then autosaves the default profile `mein_haushalt` (see the "— neu —" entry above), the selection falls back to the previous profile and the typed value is gone (shown value reverts, e.g. 4000 instead of 5321). Not reproducible with AppTest, where session state stays on the server. Suspected cause (not verified): the select is built with `index=1` only in the first run and without `index` afterwards (`_initial_profile_index` returns None once the key exists), so the frontend sends the default index 0 for the changed widget definition. Found by the level-2 tests; regression test is `xfail(strict)` `test_house_config_first_edit_after_open_is_kept` in `tests/apptest/e2e/test_smoke.py` (six open/edit attempts, so a pass by luck is below 1 %). Fix: pass the selection through `st.session_state["house_profile_select"]` (set before the widget, no `index`) instead of `index`, and decide the "— neu —" behaviour (entry above); then drop the `xfail` and move the E2E persistence tests back to the house profile if wanted.
- [ ] **EHAL-Com signal list overwrites an unreadable `components.json` with an empty document:** `ui/ehal_signal_list.py::_load_docs` wraps `_load_components_document()` in `except Exception` and substitutes `{"batteries": [], "pv_systems": []}` without any message. The table then renders from the house profile alone (11 instead of 30 rows, no error), and toggling an optional signal runs `_persist_docs`, which saves the substitute: `components.json` is replaced by an empty document (`inverters`/`batteries`/`pv_systems` all `[]`) and the page raises `ValueError: Unbekannte battery_id`. Any load failure (invalid JSON, duplicate id, validation error) triggers it, not only a hand-broken file. Found by the UI persistence tests (signal list); regression tests are `xfail(strict)` `test_t3_unreadable_components_file_is_reported` and `test_t3_toggle_never_overwrites_an_unreadable_components_file` in `tests/apptest/test_persist_signal_list_apptest.py`. Fix: fail loud (show the error, render no table and no switches) instead of the substitute, no write after a failed load (`.cursor/rules/no-implicit-fallbacks.mdc`). Same pattern in `_load_inbox` / `_load_publish_state` (bare `except Exception` → empty, the match column then reads "nie empfangen" instead of showing the failure).
- [ ] **EHAL-Com signal list: toggling a signal in Shadow mode raises `ConfigReadOnlyError`:** `ui/ehal_signal_list.py::_persist_docs` calls `save_house_profiles` / `_save_components_document` directly; in Shadow mode with a read-only config the exception is not caught and the page shows a traceback (nothing is written). The autosave forms handle this case via `ui/auto_persist.py` (caption "Shadow-Modus: Konfiguration schreibgeschützt — nicht gespeichert."). Found by the UI persistence tests; regression test is `xfail(strict)` `test_t3_shadow_mode_toggle_shows_hint_and_keeps_files`. Fix: catch `ConfigReadOnlyError`, show the same hint, disable or skip the switches in read-only Shadow mode.
- [ ] **Loxone import (Smarthome-Backend) switches the backend before the import and does not catch import errors:** `ui/ehal_greenfield_import.py::_run_import` calls `persist_ehal_backend(BACKEND_LOXONE)` (writes `ehal.backend` to `config.json`) before `run_greenfield_import(...)`; an exception from the import (e.g. `ValueError` for an unknown profile) is not caught, so the page shows a traceback while the config already says `loxone` and `house_profiles.json` is unchanged (half-applied state). Only the fetch error (`LoxoneStructureError`) is handled. Found by the UI persistence tests (greenfield import); regression test is `xfail(strict)` `test_t5_failing_import_leaves_config_untouched_and_shows_error` in `tests/apptest/test_persist_greenfield_apptest.py`. Fix: run the import first, then persist backend and house document together, and show import errors with `st.error`. Also check the pending profile select (`_SESSION_SELECT_PENDING_KEY = profile_id`): same id-versus-display-label mismatch as in the "— neu —" entry above, not verified separately.
